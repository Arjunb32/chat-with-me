This report documents the security work performed on the `Chat With Me` project during the latest implementation pass.

The work focused on the requested priority list:

- Strict Content Security Policy
- Key fingerprint UI
- Session-based key rotation with a numeric session epoch
- Metadata reduction by hiding message type from the server for new messages
- Device/session management UI
- Automated tests for encryption envelopes and message lifecycle
- Audit logs
- Argon2id password hashing for account passwords

The core verification gate now passes: `npm run check` and `npm test` both run cleanly using the portable Node/NPM toolchain placed under `.tools/`.

## 3. Major Code Changes

### 3.1 Strict CSP

Changed file:

- `src/server.js`

What changed:

- Added `buildCspDirectives()`.
- Changed CSP from a broader static policy to a stricter generated policy.
- Uses `default-src 'none'`.
- Allows only explicit sources for scripts, styles, images, media, workers, forms, and connections.
- Removed broad `ws:` and `wss:` allowances in production.
- Allows local websocket origins only in development.
- Added optional CSP report support using `CSP_REPORT_URI`.
- Added `/api/csp-report` endpoint.

Security effect:

- Reduces the blast radius of injected content.
- Prevents inline script attributes.
- Blocks unexpected external resources by default.

### 3.2 Shared Encryption Envelope Validation

Added file:

- `src/envelope.js`

What changed:

- Moved envelope checks into a shared module.
- Added validation for AES-GCM envelopes.
- Added validation for numeric session epochs.
- Rejects date-string epochs such as `2026-05-21`.
- Added message input validation that no longer requires clear message type.
- Added attachment envelope validation.

Security effect:

- Makes encryption envelope validation testable and consistent.
- Enforces the requested session epoch model.

### 3.3 Key Fingerprint UI

Changed files:

- `public/app.js`
- `public/index.html`
- `public/styles.css`

What changed:

- Added a Key button in the chat header.
- Added a Key fingerprint dialog.
- Added fingerprint display and current epoch display.
- Browser now derives a root secret from the phrase and salt.
- Fingerprint is generated from the root secret with a domain-separated SHA-256 hash.
- Per-epoch AES-GCM message keys are derived from the root key using HKDF.

Security effect:

- Both users can compare fingerprints out-of-band to confirm they derived the same chat secret.
- Message keys can rotate by epoch without changing the private phrase.

### 3.4 Session-Based Key Rotation

Changed files:

- `src/store.js`
- `src/postgres-store.js`
- `src/server.js`
- `public/app.js`

What changed:

- Added `settings.cryptoEpoch` / `sessionEpoch`.
- Added `advanceCryptoEpoch()` in both JSON and PostgreSQL stores.
- New session creation advances the epoch.
- Socket.IO sends `crypto:epoch` updates.
- Browser tracks the latest numeric epoch.
- New encrypted envelopes include `epoch`.
- Browser can decrypt old epoch messages by deriving the matching epoch key.

Security effect:

- Adds forward-secrecy-lite behavior at the session boundary.
- Avoids date-string based key rotation.
- Older messages remain decryptable when their envelope includes or defaults to an epoch.

Important limitation:

- This is not full cryptographic forward secrecy. A later compromise of the shared phrase can still derive all epoch keys unless the phrase/root material changes.

### 3.5 Metadata Reduction

Changed files:

- `src/server.js`
- `src/store.js`
- `src/postgres-store.js`
- `public/app.js`

What changed:

- Server-side message storage now uses `type: 'sealed'` for new messages.
- Public message output no longer exposes message `type`.
- Browser encrypts message kind inside the payload as `kind: 'text' | 'photo' | 'voice'`.
- The attachment upload route no longer requires `x-attachment-kind`.
- Attachments default to `kind: 'encrypted'`.
- Existing old messages with `text`, `photo`, or `voice` type keep their encrypted payloads and are no longer exposed with a public `type` field.
- A unit test now confirms new raw JSON-store messages use `type: 'sealed'`.
- A unit test now confirms legacy messages still return their encrypted payload while public output omits `type`.

Security effect:

- Server no longer learns whether new messages are text, photo, or voice from the message row.
- Server still sees operational metadata such as sender, timestamps, ciphertext size, attachment existence, and attachment size.

### 3.8 Argon2id Password Hashing

Changed files:

- `src/security.js`
- `package.json`
- `package-lock.json`
- `.env.example`

What changed:

- New account password hashes use Argon2id.
- Existing bcrypt hashes are still accepted.
- On successful login with an old bcrypt hash, the password hash is upgraded to Argon2id.
- Added Argon2 tuning env vars:
  - `ARGON2_MEMORY_COST`
  - `ARGON2_TIME_COST`
  - `ARGON2_PARALLELISM`
- Node engine was changed to `>=24.7` because native `crypto.argon2` is used when the external `argon2` package is unavailable.

Security effect:

- New account password hashes are memory-hard.
- Existing users can migrate automatically without password reset.

Important scope correction:

- This does not implement Argon2id for the browser shared-phrase KDF.
- The browser KDF currently remains PBKDF2-SHA-256 for the private phrase, followed by HKDF for epoch-specific AES-GCM keys.
- The original Argon2id recommendation was for the browser phrase KDF, so that specific item is still open.

Important deployment note:

- Production must run a Node version that supports native `crypto.argon2`, or the project must install the external `argon2` package and adjust deployment accordingly.

## 8. Known Risks And Follow-Up Items

1. Node runtime requirement changed.

   The project now expects Node `>=24.7` for native Argon2id support. If production is on Node 20, deploy will fail unless the external `argon2` package is installed and supported.

2. Full verification is still pending.

   The code should not be treated as production-ready until `npm run check`, `npm test`, and a manual app run succeed.

3. Metadata is reduced, not eliminated.

   The server no longer sees new message type, but it still sees attachment existence, ciphertext length, sender, timestamps, delivery/read maps, expiration time, and attachment byte length.

4. Session epoch is forward-secrecy-lite only.

   Epoch keys are derived from the same phrase/root secret. This improves key separation across sessions but is not true forward secrecy.

5. Old messages remain backward-compatible.

   Existing messages with clear server-side `type` are still handled by fallback logic. New messages should use sealed type.
